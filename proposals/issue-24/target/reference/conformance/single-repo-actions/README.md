# Single-repo Actions conformance

## Deterministic/local suite

From one assembled published-control-plane tree:

```bash
node --test reference/conformance/single-repo-actions/static.test.mjs
node --test reference/conformance/single-repo-actions/external-control.test.mjs
node --test reference/conformance/single-repo-actions/local-e2e.test.mjs
```

These tests cover launcher shape, external project-control loading, trusted billing-safety attestations, routing/claim/currentness behavior and a no-network lifecycle chain. They are necessary but do **not** replace the real-GitHub or real-provider release gates.

## Pre-publication real-GitHub environment

The final #40 architecture has two different default-branch roots, therefore release conformance needs two repositories that are explicitly safe to mutate:

1. a **staging control-plane repository** whose default branch contains the exact Issue #24 publication target plus only the test project-registration overlay;
2. a **disposable product repository** whose default branch contains the exact stable transport generated by this profile, with its trusted locator pointed at the staging control-plane repository.

Do not use a production/product repository, `agenti`, or `agenti-lab` as a destructive substitute.

The staging-only project registration must bind:
- the disposable product repository identity;
- selected profile `automated`;
- the current E2E Human principal;
- current `VERIFIED_NO_PAID_SPILLOVER` evidence for `claude-subscription`, attested by that configured H principal and carrying a bounded `valid_until`.

The product repository must contain only stable transport; candidate branches may modify that transport as untrusted test data but may not become bootstrap authority.

## Generic lifecycle E2E

Run the harness from the exact candidate control-plane checkout while `gh` is authenticated as the configured E2E Human:

```bash
node reference/conformance/single-repo-actions/github-e2e.mjs \
  --repo owner/disposable-product \
  --human-actor-id 12345 \
  --scenario happy \
  --confirm-disposable yes
```

Scenarios:
- `happy` — fake A/D/R → exact H release → deterministic P → Done;
- `defect` — R CHANGES_REQUIRED routes back through D before approval;
- `human` — A raises an H boundary, configured H resolves it, O reconstructs;
- `stale` — candidate-head drift invalidates old R/H/P authority;
- `stopped` — configured H Stop remains terminal across reconcile;
- `provider-smoke` — test mode is off and the **release-supported default Claude subscription route** must perform real A/D/R through the release boundary. Publication is then intentionally rejected.

The authenticated actor is not treated as authority merely because the harness knows it: runtime independently checks the external project-control Human principal before accepting Human commands.

Codex artifacts shipped in this version are experimental/unverified and are not part of the release-supported provider smoke obligation.

## Mandatory trusted-launcher security regression

In addition to lifecycle E2E, Issue #24 release evidence must exercise a PR whose candidate deliberately modifies:
- `.github/workflows/agenti-orchestrate.yml`;
- at least one A/D/R/P launcher;
- root `AGENTS.md`;
- optionally compatibility tool instructions.

The candidate should contain a visible harmless marker or alternate locator. Required observations are:
1. the PR wake is the trusted default-branch `pull_request_target` O launcher;
2. candidate O/role markers do not execute;
3. O records the trusted `product_bootstrap_sha` and staging `control_plane_sha`;
4. candidate bootstrap/tool content cannot change either binding;
5. role/P dispatch uses the trusted default-branch workflow and only loads candidate code after T0/current assignment+claim validation.

No secret-exfiltration payload is needed or permitted.

## Mandatory stale-dispatch regression

After obtaining a durable assignment bound to a known `product_bootstrap_sha`:
1. advance the disposable product default branch;
2. attempt the old assignment's role/P dispatch;
3. prove it fails before provider secret use or material authority because current trusted bootstrap/control-plane binding no longer equals the assignment;
4. let O reconstruct and prove a fresh assignment can be issued under the new trusted bootstrap.

This is distinct from ordinary candidate-head staleness and must have its own real-GitHub evidence.

## Cleanup

The harness resets `AGENTI_TEST_MODE=false` and closes disposable work artifacts unless `--keep` is explicitly requested. Release staging repositories must be reset or deleted according to the Human-approved sandbox policy after evidence is captured.

These helpers are conformance tooling, never workflow authority.
